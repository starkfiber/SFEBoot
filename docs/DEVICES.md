# Device and Windows VSS adapters — experimental

## macOS USB burner

`lib/devices.mjs` contains a real local raw-device writer and a regular-file emulation adapter sharing the streaming-write, flush and readback implementation. The 0.5 release had no physical USB available. The 0.6 raw-device branch was executed on one explicitly approved 134.2 GB USB device: 187,039,744 image bytes were written, flushed, read back and separately captured with matching SHA-256. Both Alpine entries booted from those captured bytes in QEMU. This is a one-device image-prefix write/readback qualification, not physical-machine boot or full-capacity validation. A passing QEMU USB boot tests the image/virtual transport, not macOS permissions, physical removal, sector errors or real firmware.

Read-only `burnerInventory()` uses diskutil property lists and only reports external candidates. `prepareBurn({image,device})` accepts a whole-disk identifier such as `disk4`, never an arbitrary `/dev` path. It rejects disk0, internal/unknown/nonremovable/non-USB/virtual/read-only/system/mounted disks, unknown geometry/identity, and APFS/CoreStorage descendants. Missing properties fail closed. Image bytes must fit and align to the reported block size.

The plan identifies capacity, block size, bus, registry/tree location, media name and required non-placeholder reported hardware serial; it binds these and the source SHA-256 in an exact confirmation string with a ten-minute expiry. A non-placeholder hardware serial is required; missing serial fails closed. The 0.6 adapter resolves serial from the exact whole BSD media node in the IOService registry and its USB-device ancestor. Capacity and media registry name must agree with diskutil; conflicting, absent, placeholder or duplicate serials fail closed. USB vendor/product and media/device registry instance IDs are included in the plan identity, so reconnecting requires a new plan. It never infers serial from a model or port. The bounded property-list parser does not resolve external entities; large irrelevant integer values are kept as strings to avoid precision loss. Device uniqueness, unplug/replug and real-device qualification are still required before stable support can be claimed.

`burnMacUsb({plan,confirmation,experimentalHardware:true})` is an explicit local experimental-only operation requiring administrator execution. It rechecks unmounted state/identity, snapshots and hashes the source in an owned temporary directory, verifies the character-device node and opened device identity, then writes, flushes and reads back the image range and verifies the inventory identity again. It must not be exposed by a generic HTTP/MCP execution tool or silently escalated. The writer does not automatically unmount a drive or execute remotely. One explicitly authorized physical write/readback test passed. Every new destructive operation still requires the user to select and authorize the exact disposable target.

Only source-image bytes are replaced. Bytes beyond the image remain unchanged. This release does not sanitize the whole USB, relocate backup GPT headers, enlarge partitions or guarantee that arbitrary images are USB-bootable. Cancellation/failure can leave a physical target partially overwritten; errors carry `writeStarted` and `targetMayBeIncomplete`. There is no physical rollback. Concurrent privileged writers and hostile device hotplug are outside the current experimental protection boundary.

`simulateUsbBurn({image,destination,capacityBytes?})` exclusively creates a new regular `.img` file, streams the source bytes, flushes and verifies readback. Additional capacity is a zero-filled sparse tail. It rejects existing destinations and device paths. It does not mount or write a host device. Attach the resulting file to QEMU as USB mass storage for a transport-specific boot test.

Tests executed locally: candidate-property rejection, mounted/APFS rejection, real synthetic file imaging/readback and zero tail, existing-target preservation, capacity shortfall, cancellation cleanup, symlink preservation, disabled physical writer gate. Read-only macOS inventory resolved a newly attached external USB with stable serial; it remains ineligible while mounted. IORegistry parsing, unique ancestry, duplicate/conflicting/missing serials, media mismatch and unsafe identity fixtures passed. The physical branch subsequently passed one authorized image-prefix write/readback test; broader hardware compatibility remains unqualified.

## Windows VSS acceptance script

`lib/vss.mjs` exports `vssScript({volume:'C:\\',relativePath:'fixtures/probe.txt'})`. It returns a PowerShell script; SFEBoot does not execute it. It requires a selected local NTFS volume, Windows administrator, and a functioning VSS provider. It creates one `ClientAccessible` snapshot, records its exact GUID/device object, optionally hashes a chosen file through the snapshot, and removes only the GUID it created in `finally`. It verifies that owned snapshot no longer exists and exits nonzero if creation/probe/cleanup failed. Receipt output can be redirected by an operator to a chosen new evidence file.

This is a **candidate Windows VSS probe**, not a completed backup/clone pipeline. ClientAccessible does not coordinate application writers. Do not label its results application-consistent. The transient snapshot path is invalid after cleanup. Process termination/power loss can prevent `finally`; if that occurs, recover only the recorded owned GUID, never bulk-delete all snapshots. It does not resize shadow storage, change provider services, expose a drive letter, truncate application logs or contact remote machines.

Windows VSS runtime qualification is still pending. Generation and malicious-path rejection were tested; PowerShell execution, real snapshot creation/file read/cleanup and Windows versions remain unqualified. Obtain a disposable Windows VM and an NTFS fixture for the next acceptance run. Compare a known fixture hash through the snapshot and verify that unrelated pre-existing shadow IDs survive.

The reproducible VM acceptance fixture is documented in [vm/VSS.md](../vm/VSS.md). Its acceptance criteria require frozen snapshot bytes to differ from a later live-file mutation, successful and failed probe cleanup, and preservation of unrelated shadow IDs. Preparing that fixture is not an executed Windows qualification.

## Read back a user-authorized physical burn

`exportUsbReadback({plan,destination})` opens only the exact raw source device bound to the plan with read-only flags, rechecks its unmounted identity, and captures exactly `imageBytes` into a new regular `.img`. Expected source SHA-256, destination readback, and post-read device identity must match. It does not write a device, repair its partition table or capture the untouched tail. This helper is not an MCP/HTTP tool. Booting the captured file in QEMU adds evidence about bytes read from the real drive; it still does not prove firmware boot on a physical computer. The authorized operator run now provides that write/readback evidence; physical-computer firmware boot remains untested.
